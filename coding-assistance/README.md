# AI-assisted development trace

This folder records how this project was built with AI assistance: which agents and
models were used, what each was used for, and the complete log of prompts sent.

The trace is generated from the assistant's own session database rather than
reconstructed from memory, so every entry is verifiable against primary data.

- `prompts.jsonl` — 11 recorded prompts, one JSON object per line.

### What the AI was used for

1. **Architecture and implementation** — translating a 2,076-line specification
   (`FR-001`–`FR-015`) into the layered codebase: domain models, application
   services, infrastructure adapters, the MCP surface, and the test suite.
2. **Milestone execution** — building milestones 1–10 in sequence, then Docker and
   CI/CD (milestone 11).
3. **Infrastructure and CI/CD** — multi-stage `Dockerfile`, Compose, Kubernetes
   manifest, image-verification script and staged GitHub Actions workflow.
4. **Client integration documentation** — writing and then *empirically verifying*
   the Claude Code, Codex and OpenCode connection instructions.
5. **Acceptance-criteria evaluation** — an evidence-based audit of the project
   against the review criteria, including negative findings.
6. **Writing this trace.**

Human decisions in the loop:

- Choosing the technology stack and the master specification.
- **Deciding to batch milestones 2–10 in one pass rather than gate each one** (seq 4),
  prioritising speed. Basic gates were still kept green throughout.
- Requiring that client connection commands be executed against the real image
  rather than written from assumption — which caught two documentation defects.
- Requesting and scoping the acceptance-criteria audit.

## Log format (`prompts.jsonl`)

One JSON object per line. Fields:

| Field | Type | Description |
| --- | --- | --- |
| `seq` | int | 1-based order of sending |
| `timestamp_utc` | string | ISO-8601 UTC, the authoritative timestamp |
| `timestamp_local` | string | ISO-8601 at UTC-05:00 (host machine timezone) |
| `tool` | string | AI assistant: `opencode` |
| `agent` | string | opencode agent mode: `build` |
| `model` | string | Model identifier that served the prompt |
| `provider` | string | Model provider (`opencode`, `openai`, `omnirouter`) |
| `session` | string | opencode session slug the prompt belongs to |
| `prompt` | string | Full prompt text, verbatim |
| `purpose` | string | Why the prompt was sent (authored during this trace, not from the assistant) |
| `prompt_chars` | int | Length of `prompt` after redaction |
| `prompt_sha256` | string | SHA-256 of `prompt`, for integrity verification |

`purpose` is the one derived field; it is editorial and everything else is verbatim
primary data. Entries seq 1 and seq 2 are the same 31,845-character specification
sent to two different models 26 seconds apart. They are logged separately because
they are two distinct requests. Seq 9 is a duplicate re-send of seq 8's request.

## Secret handling

No API keys, tokens, passwords or other secrets are stored here.

Redaction was applied as a structural guarantee, not merely as an inspection result:
every prompt was passed through a redaction pass before being written, matching
Anthropic/OpenAI keys, GitHub tokens, AWS access key IDs, Google API keys, JWTs,
bearer tokens, and `api_key=` / `token=` / `password=` / `secret=` assignments.

Two independent verifications were then run against the finished file. The patterns
use character classes (`gh[p]_`, `sk[-]ant`) so that this documentation is not
itself matched by the scanner it describes:

```
$ grep -cE "sk[-]ant|sk[-][A-Za-z0-9]{20}|gh[p]_|AKIA[0-9A-Z]{16}|AI[z]a|eyJ[A-Za-z0-9_-]{10}\." coding-assistance/prompts.jsonl
0
```

- Redaction pass substitutions applied: **0** — the prompts never contained secrets.
- Post-write pattern scan matches: **0**.

The credential store `~/.local/share/opencode/auth.json` was deliberately never read
or copied. Only prompt text was extracted.

## How this trace was produced, and how to reproduce it

Source of truth: the opencode session database at
`~/.local/share/opencode/opencode.db` (SQLite, opened read-only).

```sql
-- Every user-role prompt for this project directory, in order.
SELECT s.slug, p.time_created, json_extract(m.data,'$.role'), p.data
FROM part p
JOIN message m ON m.id = p.message_id
JOIN session  s ON s.id = p.session_id
WHERE s.directory LIKE '%architecture_mcp%'
  AND json_extract(m.data,'$.role') = 'user'
ORDER BY p.time_created;
```

Prompt text is `part.data -> $.text`; the model that served each prompt is
`message.data -> $.modelID` / `$.providerID`. Timestamps are epoch milliseconds and
are emitted as UTC.

## Coverage and known limitations

Stated plainly, so this trace is not read as more complete than it is:

- **12** user-role message parts exist for this project. **11** are recorded in
  `prompts.jsonl`. The single exclusion is an automated *compaction* part
  (empty text, generated by the assistant to summarise its own context) — it is a
  machine-generated artefact, not a prompt sent by a person.
- The trace covers prompts sent through **opencode** for this project directory.
  Anything sent to a different assistant, in a different directory, or before the
  database existed would not appear.
- Assistant *responses* and tool calls are out of scope for this folder; the
  deliverables are recoverable from the repository itself.
- `purpose` is editorial. Where a prompt is terse (for example "let's continue with
  milestone 2"), the purpose is inferred from the surrounding session and the
  resulting commit history.
- This trace was generated by the assistant it documents, from its own database.
  It is self-reported. The SQL above is provided so any reviewer can re-derive the
  same 11 entries independently and detect any discrepancy.
